## Journal — 03/11/2026, lot P5 (validation sur sets OMR réels)

| Hypothèse | Constat mesuré / décision | Preuve |
|---|---|---|
| Toute section MPD référencée est un sous-modèle | **Faux** : les OMR embarquent des pièces non officielles (`!LDRAW_ORG Unofficial_Part`, 31040 et 31045). Expansées, elles produisaient 28 et 99 fausses « pièces » faites de primitives. → Une section `Part/Subpart/Primitive/Shortcut`, ou une section `.dat` avec géométrie, est une **pièce feuille**. Son texte est transmis à LDrawLoader. | `tests/unit/omr-structures.test.ts`, rapport 31040 : 89 → 65 occurrences |
| R (90° autour de Y) suffit pour orienter les pièces | **Faux** : 24/65 cibles de 31040 et 13/270 de 31009 ont une autre orientation (pièce retournée, posée sur le côté, angle quelconque). → Touche **O** : on parcourt les orientations **présentes dans le modèle** pour cette pièce et cette couleur, sans révéler laquelle est attendue ; R s'applique par-dessus. | E2E pointeur 31040/31009 |
| Rotation exacte exigée | Les pièces symétriques (2×4 à 180°, 2×2 à 90°) étaient refusées dans une orientation physiquement identique. → Symétries **mesurées sur la géométrie chargée** (`yQuarterTurnSymmetries`) et acceptées par le snap. | tests unitaires, 19 poses équivalentes acceptées sur 31040 |
| Le clic pose là où le rayon touche le plan | Mesuré : la barre de pièces changeait de hauteur, donc le canevas aussi, et R3F utilisait une taille périmée pour le rayon (écart de 18–28 LDU sur environ 5 % des clics). → Barre de pièces à hauteur fixe ; le dépôt utilise la position **affichée** par l'aperçu. | E2E : 4 refus/69 → 0/65 |
| Ajout d'une dépendance npm | `npm i <paquet>` supprime les bindings natifs optionnels de rolldown du lockfile (bug npm/cli#4828). → Pour ajouter une dépendance : `rm -rf node_modules package-lock.json && npm i`, puis vérifier `node_modules/@rolldown/binding-*`. | lockfile P5 |
| Écarts déclarés au manifeste | L'ancien contrôle ne vérifiait que l'empreinte d'origine : une seconde modification d'un fichier déjà déclaré passait. → `currentSha256` obligatoire, contrôlé à chaque recette. | `npm run check:spec` |
| Journal dans `docs/09` | Décision du propriétaire : `docs/09` reste figé (v1.0), le journal vit ici ; `CLAUDE.md` corrigé et déclaré comme écart. | `spec-deviations.json` |

## Journal — 04/11/2026, lot P6 (notice ↔ 3D synchronisée)

| Hypothèse | Constat mesuré / décision | Preuve |
|---|---|---|
| Une étape LDraw, une page PDF ou un numéro imprimé identifie une étape de notice | **Faux.** 31040 : 11 étapes LDraw contre 21 étapes imprimées sur 11 pages, et 3 modèles dans le même livret, chacun numéroté à partir de 1. 31009 : une séquence 1–25 est insérée entre les étapes 36 et 37 du livret 1. → Une étape de notice est une **entrée ordonnée** (livret, page PDF, numéro imprimé, encadré éventuel, multiplicateur). Le numéro n'est qu'un libellé. | `P6_ARCHITECTURE_NOTICE_SYNC.md` § 1 |
| 3-en-1 et plusieurs livrets | 31040 : 1 PDF, 3 modèles. 31009 : 1 PDF par modèle alternatif (vérifié sur les couvertures). → Le mapping relie **un** MPD (empreinte et modèle principal) à une liste ordonnée de livrets ; seules les pages du modèle concerné sont référencées. | idem |
| Reconnaître les étapes dans le PDF | Exclu de P6, comme demandé. La couche texte expose bien les numéros (`pdftotext`), mais aucune aide automatique n'est livrée : la saisie est **manuelle**, avec la provenance `manual` ou `verified`. | `mapping.ts` |
| Mode synchronisé = nouveau moteur | Non : c'est le moteur existant avec un `StepPlan` de type `INSTRUCTION_STEPS` et le mode `synced` (candidats = étape active). Les règles de pose ne changent pas. L'étape active reste **dérivée** des pièces posées, ce qui protège contre la corruption au retour arrière. | `engine.ts`, tests unitaires |
| Empreinte du PDF | SHA-256 des octets exacts, contrôlé à chaque ouverture. Un autre PDF (autre édition) n'est jamais utilisé à la place du livret. Les octets ne sont pas stockés. | E2E « booklet change » |
| Emplacements cachés en mode synchronisé | Mesuré sur 31040 : sans fantômes, le joueur scripté échoue à la 52e pièce (tuile posée sur la face arrière, cachée). → Emplacements de l'étape **affichés par défaut** comme en mode guidé, case toujours décochable. | essai réel 31040 |
| Lecture de la page dans un panneau de 400 px | À 100 %, une page de 31040 (419 pt) était coupée. → Ajustement à la largeur par défaut en mode synchronisé et dans l'éditeur ; le mode libre garde le zoom P5 (100 %). | capture `31040-1-synced-step8.png` (hors dépôt) |
| « 2e étape sur 3 de la page » | Les encadrés étaient comptés comme des étapes imprimées. → Position calculée sur les numéros imprimés distincts de la page. | `mapping.test.ts` |
| Progression v1 (P5) | Schéma v2 : mode `synced`, livret affiché, empreinte du mapping. La v1 est toujours relue, et une v1 ne peut pas déclarer le mode `synced`. | tests unitaires et E2E « P5 progress (schema v1) » |
| Fixtures P6 | `fixtures/` fait partie de la spec figée : la fixture P6 (originale, CC0) vit dans `tests/fixtures/`. Le mapping réel de 31040 reste hors dépôt (`brick-lab-data/mappings/`). | `tests/fixtures/README.md` |

## Journal — 05/11/2026, lot P7 (bibliothèque personnelle)

| Hypothèse | Constat / décision | Preuve |
|---|---|---|
| La progression et le mapping peuvent rester dans `localStorage` | **Non** pour l'objectif : un stockage par navigateur, Chrome et Safari ne partagent rien, et les MPD/PDF devaient être réimportés. → Stockage **côté serveur local** (Node `fs`) dans `~/Documents/brick-lab-data/library/`, index JSON + fichiers adressés par SHA-256. SQLite, IndexedDB/OPFS et File System Access écartés (justification : `P7_ARCHITECTURE_BIBLIOTHEQUE.md` § 2). | `src/server/library/store.ts`, unitaires `library-store` |
| Le numéro de set identifie un modèle | **Faux** (3-en-1, plusieurs modèles principaux dans un MPD). → Set (numéro et nom modifiables, non uniques) ⊃ constructions identifiées par un id et validées par (SHA-256 du modèle, modèle principal). | unitaires « alternative models », E2E |
| Il faut réimporter 31040/31009 dans la bibliothèque | Non : découverte **en lecture seule** de `models/`, `instructions/`, `mappings/` ; fichiers référencés en place (re-hachés à chaque usage), mapping reconnu par l'empreinte du modèle qu'il contient. Le mapping est recopié dans la construction (il devient modifiable). | `discovery.ts`, E2E `library-omr` |
| Le catalogue doit recalculer progression et modes | Non : `BrickLabApp` reçoit un `BuildStore` ; restauration, validation et repli P5/P6 inchangés. Le serveur réutilise le parseur pour refuser une progression ou un mapping d'un autre modèle. | `build-store.ts`, E2E P5/P6 repassés |
| Sauvegarde automatique à chaque changement | Ouvrir une construction réécrivait la même progression ; deux onglets ouverts se mettaient en conflit sans rien faire. → Pas d'écriture si le contenu (hors date) n'a pas changé ; la position PDF enregistrée (page **et** livret) est conservée tant que le livret n'est pas rouvert (corrige aussi une perte de l'empreinte du livret en P6 avant réimport). | E2E « two tabs » |
| Une révision par modification de l'index | Importer une notice puis l'associer depuis la même page était refusé comme conflit. → L'ajout d'un fichier (additif, adressé par contenu) ne change pas la révision ; les modifications de sets et constructions, si. | unitaire « importing a file does not invalidate » |
| Réparation d'un fichier modifié de même taille | La vérification rapide (taille) ne le voit pas. → Le modèle est toujours haché (il est analysé) ; le détail d'un set hache tous ses fichiers ; l'ouverture d'une construction aussi. | E2E « modified or missing » |
| Tests E2E sur la bibliothèque réelle | Interdit : le serveur Playwright utilise un dossier temporaire (`BRICK_LAB_DATA_DIR`), et les suites refusent de tourner si le serveur pointe ailleurs. | `playwright.config.ts`, `beforeAll` des suites |
| Safari | Playwright WebKit (moteur de Safari) testé sur la même bibliothèque que Chromium ; l'application Safari reste à la recette humaine. | `library-webkit.spec.ts` |
| Boucle de rechargement en `next dev` pendant les E2E | Première hypothèse (règle `headers()` de `next.config.ts`) **réfutée** par une seconde recette en échec. Mesure : messages HMR « chunk d'entrée Next : restart » puis `reloadPage: HMR hash mismatch` à chaque connexion ; même code et même configuration : 733 / 640 navigations en 20 s avec le cache Turbopack `.next/dev` existant, **2** (5 essais sur 5) après sa suppression, avec ou sans `headers()` ; le code P6 avec son propre cache : 2. → Le serveur E2E démarre avec un cache de dev neuf (`rm -rf .next/dev && npm run dev`) ; les en-têtes restent en production seulement. Le serveur de production (`next start`, sans HMR) n'est pas concerné. | script de reproduction (navigations et messages HMR comptés), recette repassée |
| Reprendre la sauvegarde du navigateur si elle est plus récente (revue du propriétaire, 05/11) | **Insuffisant** : une ancienne partie P6, plus ancienne que les 12/65 pièces posées pendant les essais, n'aurait jamais été proposée. → Comparaison des différences pertinentes (mode, pièces posées, page, livret, empreinte des correspondances) ; choix explicite dès qu'elles diffèrent, quelle que soit la date ; récupération possible plus tard depuis le détail du set ; version remplacée de la bibliothèque toujours copiée dans l'historique (y compris dans la minute, contrairement aux sauvegardes automatiques) ; correspondances du navigateur reprenables avec la partie. | `save-compare.ts`, unitaires `save-compare` (11) et « explicit browser recovery », E2E « OLDER browser save », « another mapping » |
| Tout conflit de révision bloque l'enregistrement | Deux onglets (ou Chrome + Safari) ouverts ensemble réenregistrent chacun la page de la notice au chargement : le second était bloqué sans qu'aucune pièce ait changé (échec intermittent de l'E2E « deux onglets »). → Sur un 409, la version de la bibliothèque est relue : si la **partie** (mode, pièces posées, correspondances jouées) est la même que celle sur laquelle l'onglet se fonde, seule la vue a changé (page, livret) et l'enregistrement est refait sur la nouvelle révision ; sinon, arrêt et message « Recharger », rien n'est écrasé. La position dans la notice suit donc le dernier onglet qui l'a changée. | `build-store.ts`, E2E « two tabs » rendu déterministe (page périmée imposée) |

## Journal — 06/11/2026, lot P8 (import simplifié)

| Hypothèse | Constat / décision | Preuve |
|---|---|---|
| L'OMR a une API pour trouver les modèles d'un set | **Non** (code public du site : `routes/api.php` vide). Une page par numéro existe (`/omr/set/<n>`, non documentée). → Lue **une fois par clic**, liens `.mpd` de ce numéro seulement, téléchargement fichier par fichier sur clic ; si la page change : message, lien vers l'OMR, import manuel. | `P8_ARCHITECTURE_IMPORT.md` § 2.1, unitaires `online-sources` |
| Les notices LEGO peuvent être récupérées automatiquement | **Non** : pas d'API, identifiants de PDF différents selon la langue, conditions d'utilisation restrictives (systèmes automatisés). → Lien vers la page officielle, dépôt du PDF par l'utilisateur. | § 2.2 |
| Rebrickable est nécessaire | Non : facultatif (clé locale), métadonnées indicatives ; `/alternates/` (MOC) non utilisé. | § 2.3 |
| Télécharger par le serveur est compatible avec la spec v1.0 | **Écart à valider** : README et `docs/07` demandent que le téléchargement reste côté utilisateur. Le choix reste à l'utilisateur (un clic par fichier, rien en arrière-plan), le transfert est fait par le serveur local. `BRICK_LAB_ONLINE=0` désactive tout accès Internet. | § 3 |
| Une adresse sortante se contrôle à la validation de l'URL | Insuffisant (DNS rebinding). → Contrôle des adresses **au moment de la connexion** (`lookup` de `https.request`). `BlockList` de Node applique une règle `::ffff:0:0/96` à toutes les adresses IPv4 : règle retirée, les IPv4 mappées sont converties et vérifiées en IPv4 (formes pointée et hexadécimale). | unitaires « address », « DNS rebinding » |
| Les fichiers peuvent être inscrits dans l'index avant la confirmation (P7) | Une annulation laissait des entrées et chaque envoi une sauvegarde d'index. → `library/staging/` hors index, une écriture d'index à la confirmation, import rejouable sans doublon. | unitaires `import-p8` |
| `commit()` peut écrire la sauvegarde avant l'index | **Défaut trouvé** : une toute première écriture interrompue laissait une sauvegarde sans `library.json`, et la bibliothèque refusait ensuite de démarrer. → Index d'abord, copie ensuite. | unitaire « interrupted index write » |
| Une notice d'un set va avec toutes ses constructions | Faux pour un 3-en-1 (un livret par modèle). → Association proposée seulement pour une construction unique (« proposée, non vérifiée ») ou quand un mapping nomme le livret ; sinon cochée par l'utilisateur. | E2E `add-set` |
